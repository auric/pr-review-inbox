# PR Review Inbox: Project Brief

Status: draft 3, 2026-10-11. Scope: a production-quality personal tool for Bitbucket Server pull request (PR) review with Claude Code. Edge-case reference: PROJECT_BRIEF_GPT_ASTRA_6.md.

## 0. How to use this file

- Sections 5, 6, and 7 are spec-kit inputs. Paste each one into the named command.
- Section 6 has no technology words on purpose. `/speckit-specify` must describe WHAT and WHY only.
- Run one spec-kit cycle per milestone (section 2). Do not specify the whole product in one cycle.
- spec-kit runs many long generation steps, and they cost many tokens. A cheaper path exists: tell Claude Code "Implement milestone M1 from BRIEF.md". Do the other milestones the same way.
- IMPLEMENTATION_PROMPTS_GPT_ASTRA_6.md is an alternative prompt set with the same per-slice process. Its two-pane and general-comments-only rules do not apply here.
- Section 8 gives a workflow that you can use this week without code.

spec-kit steps:
1. Run `uv tool install specify-cli`. If it fails, use the install line from the spec-kit README.
2. Run `specify init --here --integration claude` in this folder. Run `specify init --help` to confirm the flags.
3. Once: run `/speckit-constitution` with section 5.
4. M0 (Gate 0) is an integration check, not a feature. Use prompt 0 of IMPLEMENTATION_PROMPTS_GPT_ASTRA_6.md and write `integration-check.md`.
5. For each milestone M1 to M4: run `/speckit-specify` with section 6. Add "Specify milestone Mx only" and name its stories.
6. Run `/speckit-clarify`. Answer with the defaults from section 10.
7. Run `/speckit-plan` with section 7 and `integration-check.md`. Add "Plan milestone Mx only".
8. Run `/speckit-tasks`, then `/speckit-analyze` once. Fix real contradictions only.
9. Run `/speckit-implement` for one task group per fresh session. Start each group with its acceptance test.
10. End each session with a compact handoff: completed task IDs, changed files, tests run with results, known limits, next task group.
11. Start the next session with the constitution, the spec, the plan, the tasks, and the handoff only.

## 1. Problem

- Bitbucket Server does not show what changed since I last looked. New comments and replies to my comments get lost.
- There are too many PRs. I need a fast way to understand each PR and to review it.
- I want AI review with my Claude Code subscription. The subscription works only inside Claude Code. Other tools must not use its credentials.
- AI review invents library facts and misses side effects on other code. It must use real documentation and the whole repository, not only the diff.
- AI findings are noisy. The model rates its own confidence, and nothing checks a finding before I see it. I cannot prove that a prompt change finds more real bugs with less noise.
- A small Jira task still takes much manual work before colleagues can review it. A big task often becomes one big PR that nobody reviews well.

## 2. Goals and build order

Release 1 goals:
- G1. One inbox shows every open PR that needs my attention, with unread markers and a concrete reason per row.
- G2. I follow each discussion per message. Edits, replies, and deletions show correctly. Read state survives restarts, sleep, and network loss.
- G3. I get a notification when someone replies to my comment or pushes new commits. Each event notifies once.
- G4. One click starts a Claude Code review or a cheaper Explain run of a PR.
- G5. I see what Claude Code does during a review: each tool call and each error.
- G6. Each result shows its reviewed commits, its coverage, and whether it is stale. An incomplete run never says "no issues".
- G7. I accept, edit, or discard each AI item. Only approved text goes to Bitbucket, exactly once from my point of view.
- G8. I write replies in the tool, with a preview and a confirmation.
- G9. The inbox and saved drafts work with no AI quota and with the code host offline.
- G10. Hostile PR content cannot run commands, change tool settings, or write to the code host.

Non-goals for Release 1:
- No diff viewer. Links open the diff in Bitbucket.
- No automatic review without a click. No automatic approval, merge, thread resolution, or code edit.
- Release 3 changes code only after an explicit Apply click. The app never pushes. Review v2 part 6 pushes only task branches, on a click (section 3.6).
- No team features, no hosted server, no multi-user mode, no desktop shell.
- No Bitbucket Cloud, GitHub, or GitLab. Code-host access stays behind one boundary (ForgeProvider).

Build order (each milestone is useful alone):
- M0. Gate 0: integration check on a designated test PR. Record the Bitbucket version, auth route, current user ID, paging, nested replies, real edit, delete, and reply payloads, and inline anchors. Record Claude Code and Ponytail versions, the `claude auth status` route, the `structured_output` shape with stream-json, and the Windows checks (section 7). Missing production access does not block fixture work.
- M1. Inbox, sync, read state, notifications, and minimal settings: URL and token (US1 to US4, part of US9).
- M2. Review runner with the snapshot and all safety checks, live log, and Explain (US5, US6).
- M3. Triage, publish outbox, replies, and AI reply drafts (US7, US8).
- M4. Full settings and profiles (US9).

Release 2 (plan: docs/plans/r2.md):
- Re-review: review only the changes since the last review. Each earlier finding gets a verdict: open, fixed, or outdated. Open findings carry over to the new run.
- Jira context: fetch the text of the PR's Jira issues on a click. The review reads it as untrusted data.
- Ask the PR: a question about the PR, with follow-ups in the same conversation. The answer is text only. Nothing can post.
- Read-only diff viewer: the changed files with threads and drafts on their lines. Links still open the diff in Bitbucket.

Release 3 (plan: docs/plans/r3.md):
- Fix it (author side): on my own PR, Fix works on each open, unresolved thread with a live message. This includes my own comments and posted findings. Fix also works on each open review finding that is not posted (new or accepted, with a place in the code). Each AI reply draft gets a judgement: valid, partly, invalid, question, or none. The judgement only sets the default tick in the Fix list. A read-only fix run first judges each point, then proposes exact edits. I review each edit, then click Apply. The app commits in my clone, or on an app branch that I fetch. I push by hand. A reviewer gets no Fix: "Fix works only on your own pull requests."
- Copy prompt for Claude Code: a prompt with the comment as untrusted data. I paste it into interactive Claude Code in my clone.
- Consult my session (plan: docs/plans/session-consult.md, parts A, C, and D): on my own PR, "Copy for your session" copies one plain "validate and implement" prompt with the open review points, my own threads, and the resolved threads with IDs, code, and the view of the app. The items sit in tags with a random suffix per copy, and the prompt says that the tag content is data, not instructions. I paste it into my own session in my clone. The session checks each point, implements the valid ones, and explains each rejection in plain text. The results come back through my push, "Review changes since", and Draft replies. Part C, "Ask your session" (opt-in in Settings, Clones, default off): the app lists my transcripts on the PR source branch from their metadata only, forks the picked one with `claude -p --resume <path> --fork-session` and the read tools in a sanitized snapshot, sends the same tagged items, and shows its structured verdicts in a preview. Apply makes reply drafts, discards or marks findings, and ticks the Fix list. Nothing posts. Gate B16 (CLI 2.1.301) confirmed the resume flags. The fork runs with `--no-session-persistence` and leaves no transcript.
- Consult my session, part D: the dialog offers "Judge only" and "Judge and propose fixes". The second mode uses the same fork with a higher turn cap and returns edits in the fix-run format for the accepted items. The app checks them with the fix validator. Apply of the verdicts adds them as fix cards "from your session", and the normal Review edits, Apply, and Undo flow follows.
- Jira attachments: the brief lists the attachments of a fetched issue. I download each one on a click, save it, or open its folder. Inclusion in runs is an opt-in per file.
- Jira Markdown: the brief shows the Jira text as Markdown. The server converts it from the rendered HTML.
- Tasks for every run kind: reply drafts, Ask, and fix runs show the same task chips as the brief. Each run records the tasks it used.
- Resolved threads: a resolved thread shows who resolved it and when, read from Bitbucket. The diff folds resolved threads to one line.
- Resolve threads (user decision, 2026-10-19): a reply draft with "Resolve after posting" ticked resolves its thread after the reply posts, or without a reply. Draft replies, "Review changes since" (for my posted findings that the new commits fix), a review run (for my posted questions that an answer settles), and a Fix commit propose the resolve with proof. Only threads that I started get the tick by default. The thread footer button "Resolve" or "Reopen", or the key x, acts at once and asks first on a thread that another person started. Nothing resolves without my click. Bitbucket takes no reply in a resolved thread, so a reply post reopens a resolved thread first and then posts. A ticked draft resolves it again after the reply. A failed reopen posts no reply. The post confirm and Ready to post say "Reopen thread, post reply". A draft card says "Resolved since the draft" when the thread was open at the draft. The post plan then leaves the draft out until I reopen the thread (Thread outcome). A resolve or a reopen moves the stored version and the read mark only when the stored root has the version of the first read, so an edit before the resolve still arrives. The Data Center 9.x gate confirms the PUT body `{version, threadResolved}`: the version stays, and a reply in a resolved thread gets 400 ArgumentValidationException (integration-check.md U62 to U67).

Review v2 (plan: docs/plans/review-v2/; parts 1 to 4 and part 6 here; part 7 "Autopilot replies" is on hold):
- Review quality: the finder reports every candidate with a severity and a confidence. A verify phase in the same run gives each candidate a verdict: confirmed, refuted, unsure, question, or duplicate. The app applies caps from structured fields only and shows confirmed points first. Unsure points wait in a fold. Refuted and duplicate points stay in the run record with Restore.
- Discuss a finding: "Ask Claude about this" starts a short talk about one finding, one run per message. Each answer has a verdict: upheld, revised, or withdrawn. A revision never overwrites my text. Nothing posts.
- Explain this PR: a readable walkthrough page with a reading order, checked links into the diff, risks on code, and at most 3 safe diagrams. It replaces the Explain profile run.
- Measure quality: an eval harness on synthetic fixture PRs scores recall, precision, and noise per prompt version. Settings shows outcome counts per profile and prompt version from my own triage. A discard can carry an optional reason.
- Build a Jira task (part 6, user decisions Q1 to Q24 of 2026-10-22, design.md section 10): I type a Jira key or start from the task of a PR. Claude asks a few questions, writes a short change plan, and builds the code in steps. It stops when it needs me. Nothing goes to Bitbucket without my click.
- Task sizes: small gives one PR with a short plan and the code. Medium gives a spec PR, then one code PR stacked on the spec branch. Large gives a spec PR, an optional contract PR, stacked part PRs, and an optional cleanup PR. Claude proposes the size. A migration or an API change gives at least medium. An estimate over the line budget gives large. The line budget is 400 changed lines per PR, lock files excluded, per repository. I confirm the size before any code. At most 2 code PRs of a task are open at once.
- Branches (decisions Q42 to Q45 of 2026-10-23, design.md section 10.4): the branch name is `<prefix><KEY>-<slug of the full Jira summary>`, at most 100 characters, cut at a hyphen. I pick the prefix from one global list in Settings > Tasks (default `feature/`, `bugfix/`, `hotfix/`) or type another one. No rule guesses it from the issue type. The base branch starts at my last pick for the repository, else at the default branch that Bitbucket reports, and I can search all branches. The PR targets the base branch. When the branch exists on the server, I pick "Continue on <branch>" (the default, never an overwrite) or "Start a new branch".
- Task attachments (user decisions of 2026-10-26): the attachments belong to the task, with or without a PR. The "Build a Jira task" form reads the issue on "Read the task" and lists its attachments with boxes before Claude's first step. With "Ask before Claude reads a Jira attachment" off, every box starts ticked. Else the company AI policy question comes once, as in the PR brief. The app downloads the ticked files into the task's own folder. The task screen has an Attachments tab with the same boxes and "Include all". A change applies from the next step. Every Claude step of the task gets the ticked files in `context/attachments/`: the interview, the plan, each implement step (tests, code, fix tries), and the own review. PDFs go there too. Office files and archives stay listed only.
- Tell Claude and Update from the base branch (user decisions Q52 and Q53 of 2026-10-26, design.md section 10.6): every waiting state after the build started shows a box "Tell Claude". A send starts exactly one implement step with my text as its instructions, with the same path check, checks, and own review as any implement step. The app never reads the text for git commands, and Claude never runs git. Claude can say that the branch needs the newest base, and then the app shows "Update from <base>". That button uses the base branch that I picked for each repository, for example a release branch, never a fixed develop or master. Before the first push it rebases; after it, it merges the base, so it never needs a force push. A conflict goes to a Claude step that may change only the conflicted files. When a marker remains or the step fails, the app aborts and leaves the branch as it was. The app suggests the update when the base moved or Bitbucket reports conflicts. With submodules, each repository updates from its own base, and the parent gitlink follows.
- Several repositories (decision Q46, small and medium tasks): I pick one main repository. The task workspace checks out its same-server submodules: the first level is editable, deeper levels and other servers are read-only. Claude can propose another repository, and I add or skip it. The app opens a branch and a PR only in the repositories that changed, submodule PRs first, all on one click, and each PR links the others. A large task stays in one repository.
- Sub-tasks (user decisions of 2026-10-29, design.md section 10.8): a Jira task with sub-tasks builds each sub-task as its own branch and PR. Claude proposes the order (from the base, on top of another sub-task, or after its merge) and the limit of open PRs (default 3, at most 5). I confirm both on the plan screen. Claude builds one sub-task at a time. The app tracks sub-tasks that are already in review and skips done ones. The plan run gets the ticked attachments of the parent and of each open sub-task, each issue in its own folder. It shows the Jira status of each sub-task and moves it only on my click. A sub-task that is new in Jira after the approval gets "Add to plan", and I approve the changed plan. After a squash merge of a lower sub-task, the update merges the base in three steps, so it never needs a force push. Every Jira feature works on Jira Server, Data Center, and Cloud.

Non-goals for part 6:
- No code change outside an app-owned worktree. The app never writes in my clone.
- No push without a click. No push to a branch that the task did not create, except a branch with the Jira key of its part that I picked with "Continue on <branch>". Never a push to the target branch.
- No Jira change without a click.
- No automatic approval, merge, or retarget. A retarget is one click with one confirm.

## 3. Decisions

### 3.1 Form factor: local web app

| Option | Verdict |
|---|---|
| Local web app (TypeScript server on localhost, browser UI) | **Pick.** It can start the `claude` CLI, poll Bitbucket, and keep the token local. It runs on Windows, Linux, and macOS with no extra work. LLMs write good React code. It is easy to open source. |
| Qt / QML desktop app | No. UI work is slower, and fewer contributors know it. It gives nothing that the browser lacks here. |
| Electron or Tauri | Not now. It is the same app plus packaging. Wrap it later only if you need a tray icon. |
| Static web page | No. It cannot start Claude Code. CORS blocks Bitbucket calls. Token storage is unsafe. |
| Claude Code only (skills and MCP) | Phase 0 only. Each tracking check would spend LLM tokens. |

### 3.2 How the app uses Claude Code

- The app starts the official `claude` binary in headless mode (`claude -p`). This is ordinary Claude Code use by the subscriber.
- The app never reads, stores, or forwards Claude credentials. Each user logs in to their own Claude Code.
- The app does not use the Agent SDK with subscription login. Anthropic requires API keys for that.
- No Claude Agent SDK, also not for part 6 (decided 2026-10-22). The SDK overview (read 2026-10-22) says: "Unless previously approved, Anthropic does not allow third party developers to offer claude.ai login or rate limits for their products, including agents built on the Claude Agent SDK." The SDK also falls under the Commercial Terms of Service, so it is not open source. The app keeps running the user's installed `claude -p` with the user's own login. Revisit only when Anthropic allows subscription login for SDK apps.
- Every review starts from a human click. This keeps the use "ordinary" and individual.
- Build a Jira task (decision Q5): after one plan approval, the task loop runs many Claude runs until it needs me. Each run is one bounded step. Each part stops at its PR click and at the colleagues' review. Read the usage terms again before a release.
- Before each run, the app confirms the subscription login route (section 3.5). It never falls back to paid API use.

Anthropic terms (checked 2026-10-09): "OAuth authentication ... is designed to support ordinary use of Claude Code and other native Anthropic applications." "Developers building products or services that interact with Claude's capabilities, including those using the Agent SDK, should use API key authentication." Read the current terms again before you publish the tool.

### 3.3 Most "enhanced review" requests need no app code

Claude Code runs in a sanitized snapshot of the PR head (section 3.5). It sees the full repository tree and the app's MCP servers. So these items are prompt work, not app features:
- Read project documentation: renamed CLAUDE.md files, README, docs/, ADRs. Treat them as untrusted and possibly stale.
- Find dependent code that the PR forgot: callers, overrides, config, tests.
- Check library and API facts with the Microsoft Learn MCP and the DeepWiki MCP. Send only public API and symbol names, never proprietary code.
- Compare the PR with its Jira issue. Release 2 adds this as an app connector, not as an MCP server. On a click, the app fetches the issue text through the Jira REST API. The review reads it as the untrusted file context/task.md. The review gets no Jira tool and no Jira token.

### 3.4 Polling, not webhooks

Bitbucket webhooks cannot reach a laptop on localhost. The app polls the REST API. Polling costs no LLM tokens.

### 3.5 Review safety

- `claude -p` never shows the workspace trust dialog. In an untrusted folder it still uses project hooks, the project `env` block, and `apiKeyHelper`. So never run Claude Code in a raw PR checkout.
- The app checks out the pinned PR head as a detached git worktree in an app-owned run folder. It removes `.claude/`, `.codegraph/`, `.mcp.json`, and links. It renames CLAUDE.md, CLAUDE.local.md, and AGENTS.md files.
- The runner passes `--restricted`, not `--setting-sources user`. With `--restricted`, no hook runs, also with `--setting-sources user` added (Gate B8, CLI 2.1.295).
- Gate 0 checked project CLAUDE.md and skills only with `--setting-sources user`. The snapshot rename and remove steps cover them under `--restricted`.
- `--strict-mcp-config` removes the user's MCP servers, including claude.ai connectors. `--agent rl-main` refuses the user's agents (Gate B9). Gate 0 did not check the user's own CLAUDE.md under `--restricted`.
- A review profile can add user-scope MCP servers from the top-level `mcpServers` of the user's Claude config file, with a per-tool allowlist. This is opt-in per profile. The run allows only the ticked tools and denies the other tools of each picked server.
- Never use `--bare`. It never reads OAuth credentials or the keychain, so the subscription login fails with it.
- `ANTHROPIC_API_KEY` in the environment wins over the subscription. The app removes `ANTHROPIC_API_KEY` and `ANTHROPIC_AUTH_TOKEN` from the child environment.
- Before each run, the app calls `claude auth status`. It runs only when `authMethod` is `claude.ai`. Otherwise it stops and explains. Log only `authMethod` from `claude auth status`, because its output also holds the email and organization.
- `--restricted` ignores the settings files and keeps the file tools inside the cwd (Gate B8). The app refuses a CLI older than 2.1.295.
- A separate folder is not an OS sandbox. The review gets read-only tools only, no shell, and no code-host token.
- Fix runs (Release 3) are read-only, like reviews. They get no Edit, Write, or Agent tool. They return exact text replacements in `structured_output`. The app checks each edit. It applies the edits only after the user clicks Apply.
- The app never runs `claude` in the user's clone. A fix run uses the same sanitized snapshot as a review.
- Implement runs (Review v2 part 6, decision Q1): kind implement gets Read, Grep, Glob, Edit, Write, and the read-only git MCP. It also gets the MCP tools that the user ticked in the profile of the task, with the review run flags: `--mcp-config`, the ticked tools in `--allowedTools`, the other tools in `--disallowedTools`. A picked CodeGraph server indexes repo/ of the part before each step. The app deletes that index before the path check. The skills of the profile go to context/skills, outside repo/. It gets no shell, no Agent tool, and no web tool. It runs only in an app-owned worktree of the cache, never in the user's clone.
- Every step of a task (interview, spec, each implement mode, and the own review) uses the profile that the user picked for the task, with its skills and MCP tools. Each step reads the profile at its start, as a review run does. Gate B17 (CLI 2.1.306) confirmed that `--restricted` keeps Edit and Write inside the run folder. Review, re-review, Ask, reply, fix, discuss, Explain, interview, and spec runs stay read-only.
- PR context and notes (Review v2 part 2): reply, review, re-review, fix, and Ask runs get context/pr-context.md as untrusted data, and context/notes.md with the notes that the user wrote or kept. Explain and session runs get neither. The app builds both files again before each run with app code only: no Claude call and no memory between runs. stdin never holds note, comment, or PR text. A note that Claude proposes reaches no run until the user keeps it. A proposal needs a live message of the user in its thread, so a comment of another person alone cannot plant one.
- The task worktree uses sparse checkout. `.claude/`, `.mcp.json`, `.codegraph/`, CLAUDE.md, CLAUDE.local.md, AGENTS.md, `.gitmodules`, and hook sources are absent on disk. It sets `core.symlinks=false` and an empty `core.hooksPath`. Commits run no hook.
- After each Claude step, the app runs `git status`. A denied path (Denied paths, section 7), a link, or a path outside repo/ fails the step. The app saves the changes as a patch, then resets the worktree to the last commit.
- App-run commands (decision Q2): Claude never starts a process. The app runs only the build, test, and lint argv lists that the user approved with the plan. Each command has a timeout and a process-tree kill. No shell form exists. The first plan of a repository shows one warning, and the user clicks "I understand". The env is the scrubbed child environment plus CI=1, with no token. HOME is a temp folder by default.
- Not enforceable: a test or build command runs code that Claude wrote. It can read the user's files and reach the network. Native Windows has no OS sandbox. Safeguards: the plan approval, the own review, the user's look at each PR before the push, and the first-use warning. A WSL2 or sandbox runner comes later.

### 3.6 Local server safety

- Listen on 127.0.0.1 only. A random port is not authentication.
- Check the Host and Origin headers on every request. Use Hono `csrf()` on mutations. Never enable wildcard CORS.
- Every mutation needs a per-start session token. The server puts it into the page it serves.
- Outbound calls go only to the configured Bitbucket instance. Check redirects against it. Two exceptions: a review with a Docs profile lets the CLI call the documentation MCP servers (Microsoft Learn, DeepWiki). A profile with user MCP servers lets the CLI start or call those servers. The app also calls them for tools/list in Settings and at run start. A remote user server needs https, except on localhost.
- Outbound calls can also go to the configured Jira origin. They occur on a Settings save, a Fetch, Read the task, Build this task, Read Jira again, Add to plan, and Move in Jira. For a task that builds sub-tasks, the sync reads the status of its sub-tasks with one GET of the parent at most every 5 minutes. The Task view reads it at most once per minute. The Jira client sends GET only, except one POST of a transition after the user confirms "Move in Jira". It follows no redirect and calls no other origin.
- For a task that builds sub-tasks, the spec run also reads the branches that name each sub-task key, the open PRs of the repository, the changed paths of each tracked PR, and the newest merged PRs of the repository. These calls are GET only.
- Release 3: a Download click also calls Jira. The attachment download follows same-origin redirects only, at most 3 hops. It checks the origin and the base path on each hop. A cross-origin redirect is an error, so the token never leaves the Jira origin.
- Release 3: the app runs git in the user's clone only on a clone check, Apply, and Undo. It runs no git network command there. Apply and the confirm of a post call Bitbucket once for the live PR state.
- Review v2 part 6 (decision Q3): `git push` and PR create or update go to Bitbucket only on a click. A push goes only to a branch that the task created, or to a branch with the Jira key of its part that the user picked with "Continue on <branch>". It never goes to the target branch or to the branch of a PR that the app tracks but did not create. It always has an explicit `--force-with-lease`. The refspec never has a `+`, because git then ignores the lease. The app refuses any other refspec before git runs. A normal push must be a fast-forward of the last pushed commit, else the app asks for a force. A force push after a rebase needs a confirm and keeps the lease, so it never overwrites a colleague's newer push. "Update from <base>" (decision Q53) rebases only before the first push and merges after it, so it never needs a force push. After a squash merge of a lower part, the update merges the base in three steps (spec section 6.20.10). The app never force-pushes after the first push. The push runs from the cache, not from the user's clone. The token goes in the GIT_CONFIG env, never in argv, the worktree, or logs. The token needs Repository write.
- Review v2 part 6 also reads the build stats of a commit and the clone links of the repository. On "Build a Jira task", the Jira client fetches the key that the user typed (decision Q4). The form's "Read the task" click reads it once before, and the create click and a tick in the Attachments tab download the ticked files (section 6.17 of the spec). Decisions Q42 to Q46 (2026-10-23) add GET reads only: the default branch, the branch search, the repositories with write permission, the branch restrictions, and the merge commit of a merged PR (Gates G13 to G17). The app sends no request to the origin of a submodule on another server.
- Review v2 part 2 (PR context): before each run, the app reads the build stats of the PR head and refreshes note links older than 10 minutes (at most 5 PR reads). After Gates G9 and G12 pass, it also reads the open PRs of the repository (one page of 50) and the change list of each one that is not stored (at most 30, cached by PR and update time). Until then it lists only the open PRs that the app stores. All reads of one build share 15 s and stop on Cancel. A failed read keeps the stored part, and the run goes on. These calls are GET only.
- Build status (docs/plans/ci-builds.md, Layer A): each sync cycle reads the build stats of the head of each open followed PR. When they change, it reads the build statuses of that commit once. These calls are GET only. A build link opens only in the browser.
- Stack order (Gate G5): Bitbucket declines an open PR within 30 s when its target branch is deleted. So the app retargets the upper PR before the lower branch is deleted, for example before a lower PR merges with "delete source branch". The app never deletes a lower branch while an upper PR targets it. The part PR text asks the merger to keep the branch until the next PR moves.
- Attachment files are served as downloads (`Content-Disposition: attachment`, `application/octet-stream`, `nosniff`, `Content-Security-Policy: sandbox`). Inline display is for raster images only: PNG, JPEG, GIF, and WebP by magic bytes. SVG and HTML are never served inline. No browser request goes to Jira.
- Support a corporate CA file. Never disable TLS verification.
- The Bitbucket token lives in the OS credential store through `Bun.secrets` (experimental; verify in Gate 0). Fallback: memory only, asked again after a restart. The Jira personal access token (Release 2) uses the same store under its own name.
- The tokens never go into SQLite, localStorage, URLs, logs, or prompts. Logs are redacted. No telemetry.
- Render comment Markdown safely. Never fetch external images from untrusted comments automatically. Skip raw HTML. A link URL with a scheme stays only for http(s). Relative URLs and fragments stay. An image source `attachment:<id>` (Release 3) maps only to the local image route of a downloaded raster image.

### 3.7 Stack and scope choices

| Choice | Reason |

Flow of one review:
1. The user clicks Review and picks a profile. The server returns the existing job if one is active for the same PR, commits, and profile.
2. The server checks the CLI version and `claude auth status`. It stops with a clear message on a wrong route.
3. The server fetches the PR head into the bare cache and pins the source, target, and merge-base commits.
4. The server exports the snapshot, removes dangerous files, and writes the PR context files next to it.
5. The server starts `claude -p` with a scrubbed environment and sends the prompt on stdin.
6. The server streams Claude events to the UI: tool calls, errors, progress.
7. Claude returns structured JSON. The validator checks the schema and every file and line against the snapshot. Review v2: the app then runs the verify phase, a second CLI process in the same snapshot, and applies the caps (section 7, Verify phase).
8. The user triages the items and approves exact texts. The server posts through the outbox and reconciles the outcome.
9. The server deletes the snapshot folder.

## 5. Paste into /speckit-constitution

```
Review Loop principles:
1. Human gate: nothing goes to the code host without an explicit user action. Approval binds the exact text and destination. Editing the text removes the approval.
2. Untrusted input: PR titles, descriptions, code, comments, and repository files are hostile. They can contain prompt injection or executable configuration. Review runs use a sanitized snapshot, read-only tools, and no code-host write access. The app posts, not the AI. Exception (decisions Q1 to Q3, 2026-10-22): implement runs of a task get Edit and Write only in an app-owned worktree, never in the user's clone, and only after Gate B17. The app, not the AI, runs the user-approved commands and pushes task branches on a click.
3. Credentials: the app never reads, stores, or forwards AI-provider credentials. It starts the user's own official Claude Code CLI with the subscription login. It never falls back to paid API use. Code-host tokens stay in the OS credential store or in memory.
4. Zero-token tracking: polling, unread state, notifications, and publication never call an LLM. Only reviews, explanations, drafts, fix proposals, Ask answers, and task steps use tokens.
5. One review runs at a time by default. Each run shows the usage that the CLI reports. No automatic retry after a usage limit. A task loop takes the run slot for each Claude step and frees it between steps. After one plan approval, it runs many steps until it needs the user (decision Q5).
6. Revision-pinned evidence: every result names the commits it reviewed. A result for older commits shows as stale.
7. Honest coverage: every result lists what it read, skipped, and could not reach. An incomplete run never reports "no issues".
8. No blind retry: after an unknown write outcome, reconcile with the code host first. Never claim exactly-once delivery without server support.
9. Private code stays private: never put proprietary code, internal URLs, or PR text into public documentation queries.
10. Deployment prerequisite: the company authorizes sending source code to Claude and using the documentation services.
11. Three expansion boundaries: ForgeProvider, ReviewRunner, ContextSource. Build each one only when its milestone needs it. No other plugin layers.
12. Routine tests use sanitized fixtures and a fake Claude CLI. Real-server tests run only with separate authorization.
13. Minimal UI: few screens, few options, good defaults, full keyboard use. Add a setting only when a default fails.
14. Local-first: all data stays on the user's machine. No telemetry.
15. Small and boring: use the standard library and platform features first. Add a dependency only when it saves real work.
16. Open-source ready: no company names, hosts, or secrets in the code. The config holds all instance details.
```

Never a `+` refspec: git then ignores the lease. A normal push checks the fast-forward first, else it returns "needs force". A confirmed force push skips only that check. A stale lease fails with `[rejected]` and `(stale info)`, and the remote keeps its commit (G6). The app then offers "Get their commits", with no force.
- Stack order (G5): when the target branch of an open PR is deleted, Bitbucket declines that PR within 30 s and keeps the deleted branch as its toRef. Retarget the upper PR before the lower branch is deleted. Never delete a lower branch while an upper PR targets it. A declined upper PR gets "Open the PR again". A reopen with a deleted toRef is unverified.
- Error mapping: 401, 403, 404, and 409 give one sentence and one button. A 409 on create, or a create with an unknown outcome such as a timeout, reads the open PRs of the branch and links the match. The app never posts a create twice.

Sync rules:
- Poll followed active PRs about every 60 s. At most 2 concurrent requests. Add jitter. Back off on errors. No source or full diff downloads during polling.
- Follow the server's paging fields (isLastPage, nextPageStart). Never compute the next page. Treat a missing nextPageStart and nextPageStart: null the same: both mark the last page.
- Detect truncation and capped responses. Record them as incomplete, never as complete.
- Activity IDs form a seen-set. Do not assume they are ordered. Do not rely on updatedDate or local clocks.
- A seen-set misses edits, replies, and deletes, because they create no new activity. On each poll of a followed PR, compare each comment's version and its nested reply IDs with stored state.
- Comment identity: instance, repository, PR, comment ID, plus version.
- Flatten nested replies. Keep the parent ID and the root thread ID.
- Advance checkpoints only after the database transaction commits.
- Resume safely after sleep, VPN loss, and restart. A partial or failed fetch never deletes anything.
- Deletion needs two checks. A complete activities fetch (all pages) does not contain the comment. A direct GET of the comment returns 404. Only then mark it deleted. The app keeps its own local tombstone, because the server keeps none.
- First sync of a PR imports history as read and silent. Own events never create unread markers or notifications.
- Reconcile followed threads on every poll. Edits, replies, and deletes show only as comment changes.
- A merged or declined PR stays followed until the user archives or unfollows it.

Read state:
- An acknowledgement stores comment identity plus the acknowledged version. Mark-read sends the exact IDs and versions that the UI showed. A newer version or a new comment stays unread.
- Unread is separate from provider state and from review state.

Flags: as the finder, with `--json-schema verifyJsonSchema()`, the verifier model or the profile model, `--effort` of the verifier (default medium), and min(profile cap, 10 + 3 per candidate) turns, at least 12. Above 12 candidates it gets rl-verifier, with at most 6 candidates per call. Verifier mode off skips it, and the items show "Not checked".

A finding of module rules must quote a sentence of a loaded instruction file. Else it drops with reason "rule". A quote from a file whose scope does not cover the path keeps the finding, with module core and no rule. Kept findings with overlapping anchors on the same path and side form one group, also by transitivity. The verifier judges sameness inside a group only.
- Caps (Review v2): refuted and duplicate candidates become discarded items with discardedBy "verify", shown in the run record with their reason and Restore. A question verdict, or an empty trigger without a confirmed verdict, gives a question item. An unsure verdict, or evidence status unverified without a confirmed verdict, caps the severity at minor. The app never matches words in the text. The display group comes from the check state, the severity, and the run volume at read time.
- Discuss (Review v2): one run of kind discuss per user message, with no Agent tool and no resume. The workspace is at the current heads. context/finding.md holds the finding with its verdict and my current text. context/discussion.md holds the earlier turns, newest last, with a 40 KB cap. The message is the only content of "Your instructions". At most 20 messages per finding, 4,000 characters per message, 8,000 per answer, 40 turns per run. upheld changes nothing. revised stores a revision item (status discarded, payload revises <finding>) with Use the new text and Keep mine. withdrawn discards the finding with a mark and Restore. On a posted finding, a reply becomes a reply draft with origin discuss and the writer rank of a reply run; withdrawn also proposes resolve, ticked on threads that I started. A finding that changed during the run gets nothing. Ready to post, the post plan, history.md, and the counts skip finding revisions. Nothing posts.

It uses the Explain profile, no Agent tool, no history.md, and no questions.md. The server checks each `diff:<path>#N<line>` or `#O<line>` link against the change and turns a bad link into plain text. It keeps the first 3 mermaid blocks of up to 20,000 characters, turns the others into text blocks, and strips `%%{` lines. explain_json holds the result. The page `/:view/:project/:repo/:id/explain` (key w) shows the newest result, marks it stale when the heads move, and runs again only on a click. Old explain runs (kind review, explain 1) keep their run line.
- Measure (Review v2): `bun run eval -- --real` runs the review pipeline with the real CLI on synthetic fixture cases in temp repositories and a temp database. It scores items by path, side, and line overlap with both ends inclusive. Without `--real` it exits 2 and starts no process. GET /api/stats/review counts per profile and prompt version: runs, candidates, refuted, unsure, shown, accepted, edited, discarded by reason, posted, addressed, outdated, time, and usage. - PR context (Review v2 part 2): context/pr-context.md holds the PR text (description cut at 4 KB), the linked tasks, the build counts of the head, the threads of the run in full text, every other thread as a digest with its State line, and the other open PRs that change the same paths (exact path or src path match). The State line is the outcome line of the PR view (src/shared/outcome.ts), so the file and the UI never disagree. The file stays at or under 48 KB: the focus threads get 24 KB and drop their oldest messages after the root first, the other PRs get 10 entries and 6 KB, and the other threads fill the rest in a fixed order. Count lines name what is left out. The same rows give the same bytes.
- PR notes (Review v2 part 2): the Notes block under the description lists kept notes, each with an optional PR link and its state chip, and Claude's suggestions with Keep, Edit, and Dismiss. A reply run can propose up to 2 notes and cite up to 5 other threads. The app drops a proposal without a live message of the user in its thread, a repeat of any note text, and a proposal over 30 notes, and drops a cite of an unknown thread. The proposals and the drafts of a run go in one transaction. A draft card shows its suggestions and a "Based on the thread of" line. `bun run eval -- --replies --real` scores reply runs on fixture cases by judgement, action, and cites.
- Task runs (Review v2 part 6): interview and spec runs are read-only in a sanitized snapshot of the target head (a replan reads the spec branch). Implement runs work in the task worktree (section 3.5). The own review of a part is kind review with task set, on the part base..head, in a sanitized snapshot of the commit. Submodules (decision Q46): only task workspaces check out same-server submodules, each from its own cache as a worktree at its path. The first level is editable; deeper levels are read-only; other servers stay empty folders. A change in a read-only repository fails the step. The interview and spec snapshots hold the readable submodules as sanitized read-only folders. The PR review snapshot and the own review keep "No submodules"; the own review runs once per changed repository. Every task run is a review_run row with task set and pr NULL. It shares the one run slot, the log, cancel, usage, and restart recovery. No PR view, run list, Ready to post, or stats show it. The restart recovery marks a running task run failed.
- Interview: structured questions with options and a recommended answer, at most 2 rounds. Spec run: the plan files, the tasks, and the estimate (parts, changed lines, files, db and api flags). The app applies the size rules (section 2). Plan approval stores the picked commands per repository.
- Task loop of one part: a tests step whose new tests must fail, then per task an implement step, the checks, at most 3 fix steps, and a commit that ticks the task. A part over the line budget stops and proposes a split. Then the own review (finder and verify phase) fixes confirmed blocker and major points, at most 2 tries. Minor points stay listed with "Fix these too". Then the part waits for its PR click. Each stop says why and offers one button. Resume restarts the stopped step from the last commit and keeps the discarded changes as a patch file.
- Living spec: a step that changes a file under the spec folder stops for the user. Accept keeps the commit on the spec branch or the part branch.
- Tell Claude and the base update (decisions Q52 and Q53, spec section 6.18): an instruct step is an implement run whose "Your instructions" hold my text. A resolve step is an implement run that may change only the unmerged paths of a paused rebase or merge. The app runs every git command, checks for conflict markers, runs the checks, and aborts and resets every repository on a failure. The PR sync stores properties.mergeResult of task PRs to suggest the update.
- Part gate: the next part starts when the PR below it has at least 1 approval, no Needs work, no open blocker task, and green or no builds. One confirm overrides it. At most 2 open code PRs per task. After a lower PR merges, the app proposes the retarget of the next PR (one click, one confirm). After a squash merge, the update merges the base in three steps (spec section 6.20). It never needs a force push. "Push and move" pushes and retargets in one click with one confirm. A replan run after each merge proposes changes to tasks.md for the user's approval.

The pure function nextPart (src/server/tasks/schedule.ts) picks the next part from its start mode (base, stack, merge), the part gate, the limit of open PRs, and one build at a time. XState covers only the task and part machines. After a squash merge of a lower part, the update merges the base just before the squash commit, records the squash commit with `-s ours` after a tree check, and merges the rest of the base. A failed check takes a plain merge with the resolve step. The app finds branches and PRs of a sub-task by its key as a whole token. It tracks a PR that it did not create and never pushes to it.
- Task notifications: needs you, a part ready to open, and spec approved. One tab claims each event.

Job states: running, completed, incomplete, cancelled, failed. There is no queued state. Freshness is computed on read: a result turns stale when the source or target head changes. One run slot: a start while another run uses it gets 409 with the running run. Job start is idempotent: the running-job key is PR, source head, target head, profile ID, profile revision, and the note hash (a reply run adds its threads). A second tab or a refresh with the same key gets the existing run.

Output contract (zod, schema-versioned):
- Identity: schema version, PR identity, source and target heads, merge base, job ID, session ID, CLI version, profile and skill revision, model, context fingerprint.
- Explanation: intended behavior, changed areas, material assumptions.
- Findings: category, severity (blocker, major, minor, nit), confidence, location (path, line, side new|old), triggering scenario, evidence references, evidence status (code-grounded, reproduced, unverified), consequence, suggested direction. Review v2 adds title, trigger, cause, rule, and module, each with a default, and stores the verify result {verdict, reason, evidence, severity, duplicateOf} in the payload.
- Questions: question, why it matters. Never mixed with findings.
- Coverage: files and documents read, content skipped or truncated, unavailable tools or repositories, tests run or not run.
- Deterministic validator: reject malformed output. Check every path and line against the snapshot. Invalid references become coverage problems, not findings. A schema-valid result is not proof of a correct review.
- Malformed output: at most one format-repair call, then the job fails with the raw output kept.

Publication:
- A post row is the approval. It binds the exact body, the destination (general, reply, or inline anchor), the item revisions, and the reviewed commits. Its idem_key holds the item revisions, so an edited item gets a new row.
- Preflight before send: refresh PR state, heads, and comments. Block stale items and show the reason. Flag likely duplicates against existing comments.
- A reply post checks only that the parent comment still exists and that no newer message arrived in the thread since the user saw it. It does not check the heads.
- Inline anchors pin fromHash and toHash to the reviewed commits. A line outside the diff goes into the general comment.
- Durable outbox states: pending, sent, unknown, failed, confirmed. Save the remote comment ID and version on success.
- A timeout after send sets unknown. Reconcile against remote comments before any retry. If still unclear, the user decides.
- Publish is idempotent on the server side: one outbox row per approval. A second tab or a refresh never sends twice.
- The backend posts. Claude never posts.
- "Fixed in" reply (Release 3): after a fix commit, the app supersedes the thread's open reply drafts that I did not edit or accept, and stores their IDs in the new draft. It adds a reply item "Fixed in <short hash>.". A thread with a draft that I edited or accepted keeps it. The "Fixed in" text, my draft text plus the "Fixed in" line, waits as a revision of my draft, and the fix run lists it in its coverage. Use revision of it names my draft in fix.replaced, so Undo of the commit brings my draft back. A thread with a "Won't fix" draft keeps it and gets no "Fixed in" draft. Undo of the commit discards the "Fixed in" draft and brings back the newest replaced draft while the thread has no open draft. A "Fixed in" draft of an undone commit cannot come back. The item posts only when the PR commits list the commit and were fetched for the current heads. Else the post plan lists it as blocked: unpushed "Commit <short> is not on the PR source branch yet. Push it. The next sync finds it.", or commit-gone when the clone branch of the fix no longer holds the commit. A commit-gone draft offers "Post as plain reply" (Thread outcome).
- Fixed finding (Release 3): a fix commit discards each open finding (new or accepted) that it covers and marks it "Fixed in <short hash>". The finding leaves Ready to post. Restore returns the finding to its earlier status and keeps the mark ("You restored it"). A restored accepted finding is back in Ready to post. Undo of the commit also returns the earlier status of each finding that the mark still discards, and removes the mark.
- Session consult (S1, S2): a consult run row holds one imported answer of a session run, or a pasted answer from before 2026-10-20. It starts no process, and no run list shows it. A session run (kind session) holds the answer of a fork and the item keys at its start, never transcript text or the transcript path. A session reply draft says "Your session". A session reject discards a finding and keeps the reason until a restore or Undo. A session accept ticks any row of the Fix list.
- AI mark (setting, on by default): the post plan puts "🤖 " once at the start of each post built from an AI item (finding, question, reply draft, edited or not). A manual reply never gets it. The outbox keeps the marked text, so confirm, send, and reconcile use the same bytes.

Thread outcome (docs/plans/thread-outcome.md):

Markers: Out of date, Resolved since the draft, Code changed, Waiting for push, Revision waiting.
- The UI derives the outcome from the reply draft, the fix note, the fix commit, and the thread state. It needs no migration.
- Outcome line: a thread with a reply draft card or a fix card shows the line on top of that area. First match wins: Resolved without an open draft, my decline, a fix commit, my open draft (accepted, edited, or mine), the newest fix result, an AI draft, then Waiting on them or Open. On my own PR a valid or partly valid judgement reads To fix. A session accept reads To fix, also without reply text. When I untick every free edit of a thread, its open draft states the outcome.
- Conflict note: a note between the line and the cards when they disagree. An open reply that judges the comment not valid next to ticked edits: Keep the reply unticks them, Keep the fix discards the reply. An untouched open reply that asks for a fix next to a fix note with why already, invalid, or scope: Keep the reply accepts it, or runs Fix anyway when it has no text; Keep the fix discards it and restores the nofix draft of that run. A finding that my session rejected, with ticked edits: Keep the reject unticks them, Keep the fix restores the finding.
- The reply draft card names its writer: the review, the reply run, my fix commit, the fix run, my session, the re-review, or me. The Draft replies button counts the your-turn threads with no current draft, or with an out-of-date draft that a run for all threads replaces or revises. A thread whose waiting revision answers the newest message does not count. The run still takes every your-turn thread.
- Fix anyway: the fix-run request takes `anyway: true` with exactly one thread or finding. The prompt says that I chose the fix despite the earlier note and asks for edits unless no edit can make the change. The run key adds "anyway".
- Writer priority: my edit, accept, or decline, then "Fixed in", then the no-fix draft of a fix run, then a reply run or the answer draft of a review run, then a resolve-only proposal. A writer never replaces the draft of a higher writer. It lists "Thread N: kept your draft" in its coverage. A reply run for threads that I name is my choice, so it replaces an untouched AI draft of any writer.
- No-fix draft: a thread note with fixed false and why already, invalid, scope, or unclear makes an unaccepted reply draft with origin nofix and the note reply as its body. already also proposes resolve. Only a thread that I started gets the tick. why decision, risk, and dropped make no draft. A finding note makes no draft.

- "Fixed in" text: the draft keeps an untouched answer of a reply, review, or session run, then adds "Fixed in X: <what>". what is the note reply. A commit that holds only a part of the edits of a thread, together with the other commits of its run that are not undone, gives "Partly fixed in X" and no resolve proposal.

The card shows a word diff of the revision against my text: struck text leaves, underlined text comes in. A revision without text and without a resolve stays discarded as my choice. Keep mine (keep-mine) drops the revision, and my exact text stays with its accepted state. A newer revision of a thread drops the older ones. A dropped revision keeps its row with dropped true, because SQLite gives the ID of a deleted last row again. The app then copies the file once to config.json.bak (or the next free config.json.N.bak) and logs the dropped key, because the next save writes the file without it. A save writes config.json.tmp and renames it. When another program holds config.json open and the rename fails with EPERM, EACCES, or EBUSY, the app tries again for about 500 ms.
